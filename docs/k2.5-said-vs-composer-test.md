# K2.5 + said-orchestration vs Cursor Composer 2.5 — Test Protocol

**Pre-registered** (write the judging rules before seeing results, so neither side
can move the goalposts). Status: protocol locked; awaiting the `said-orchestrate`
binary (in-progress wiring) to run.

## The question

Cursor's Composer 2.5 **is** Kimi K2.5 + their proprietary RL (textual-feedback RL
on coding/agent traces, baked into the weights). Advisory's approach is the SAME
base model + `.said` memory/playbook at inference time (no RL).

**So, holding the base model constant (Kimi K2.5), which way of making it a great
coding agent wins — RL-into-weights (Composer) or memory-orchestration (`.said`)?**

This is the only test that controls for the model. Same base, two harnesses, one
gate as judge.

## The two arms

| Arm | What runs | Represents |
|-----|-----------|------------|
| **A — `.said`** | Kimi K2.5 (via OpenRouter) → `said-orchestrate` binary (plan→design→code→test→repair→learn) → `.said` memory + playbook → gate | memory-orchestration, no RL |
| **B — Composer** | Cursor Composer 2.5 (= K2.5 + Cursor RL) → driven by `cursor-agent` CLI on the same repo → gate | RL-into-weights |

**Constant:** base model = Kimi K2.5. **Varied:** only the harness (memory vs RL).

## The judge (same for both — no human scoring, no vibes)

The Advisory repo's gate: `dotnet build` **and** `dotnet test` both green. A run
"passes" only if the change builds + tests pass. This is the SOLE success signal
for both arms — identical to how the mutation cycle already gates.

## Tickets (the test set)

- **N = 12 tickets**, all PR-only, all gate-checkable, drawn from the Advisory
  `mutation`-labelled backlog + fresh tickets of known shape.
- **Two buckets, reported separately:**
  - **6 "recurring-shape"** tickets (e.g. add-anonymous-GET-endpoint+test) — where
    `.said` memory/fix-replay SHOULD help most. This is where Arm A's advantage,
    if real, shows up.
  - **6 "novel"** tickets (different shapes the brain hasn't seen) — where memory
    should help LESS. Tests honesty: if Arm A wins uniformly, something's leaking;
    if it wins on recurring and ties on novel, that's the expected, credible signature.
- Each ticket run in BOTH arms (paired), same repo state, same prompt intent.

## Metrics (decide the winner)

| Metric | Why it matters | Primary? |
|--------|----------------|----------|
| **First-attempt pass rate** | builds+tests green with ZERO repairs — exactly what Cursor's textual-feedback RL targets | ⭐ PRIMARY |
| **Repairs-to-green** | avg repair loops to pass (fewer = better) | ⭐ PRIMARY |
| **Pass@1 (reached green at all)** | did it produce a mergeable PR within the retry budget | yes |
| **Tokens / cost** | memory adds input tokens but should cut repair loops; RL adds none | yes |
| **Wall-clock to green** | end-to-end latency | secondary |
| **Diff quality (surgical?)** | lines changed; no unrelated edits | secondary |

Retry budget: **max 2 repairs** for both arms (the Advisory cycle's default).

## Fairness rules

1. Same base model (K2.5), same temperature, same retry budget, same gate.
2. Same tickets, same starting repo commit per ticket, run paired.
3. The gate alone decides pass/fail — no human judgement on correctness.
4. Report ALL runs (including failures); no cherry-picking.
5. Report the recurring-vs-novel split, not just the aggregate.

## Honest caveats (so the result isn't misread)

- **`.said` recall must actually work for Arm A to be fair.** said 0.9.0 has an
  incremental-indexing bug (added frames aren't retrievable) — if Arm A runs with
  broken fix-replay, it UNDERSTATES the memory approach. Run Arm A only with a
  recall path proven to retrieve (the 0.7.0 code-frame path / WASM, or a fixed
  binary). State which path was used.
- **Composer 2.5 is a finished, shipped, RL-tuned product; `said-orchestration`
  is new.** A close result favours the memory approach (it has no RL and is
  model-agnostic). A loss on novel tickets is expected and not damning — memory
  helps recurring shapes most.
- **The real strategic win for `.said` isn't "beats Composer on K2.5"** — it's
  that the SAME memory works on ANY model with zero retraining, and updates
  instantly. Even a tie on K2.5 proves the thesis: you got Composer-class lift
  from a portable file instead of a GPU farm.

## Run plan (when the binary lands)

1. Wire `said-orchestrate` with `OPENROUTER_API_KEY` + `moonshotai/kimi-k2.5` +
   the dotnet gate against an Advisory clone.
2. Install/auth `cursor-agent`; confirm it runs Composer 2.5 headless on the clone.
3. For each of the 12 tickets: run Arm A, run Arm B, record all metrics from the gate.
4. Tabulate: first-attempt pass, repairs-to-green, pass@1, cost — split by
   recurring vs novel.
5. Write up with the raw per-ticket table (no aggregation hiding).

## Expected outcomes (pre-registered prediction)

- **Recurring shapes:** Arm A (`.said`) ≥ Arm B — memory/fix-replay should match or
  beat baked-in RL on shapes it has stored.
- **Novel shapes:** Arm A ≈ Arm B or slightly behind — no memory to recall; both
  run raw K2.5-class reasoning.
- **Cost:** Arm A higher input tokens (recall context), Arm B higher per-token
  price (Cursor's markup) — net likely favours Arm A.
- **The headline either way:** if memory-orchestration ties or beats RL on the same
  base, portable model-agnostic memory is validated as a Composer alternative.
